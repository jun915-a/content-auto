Variables, functions, and modules should use `snake_case` to reflect their procedural nature. For example, `calculate_total()` instead of `CalculateTotal()`. Types and enums, however, use `PascalCase` (`HttpResponse`, `ErrorKind`) to distinguish them from runtime entities. Avoid abbreviations unless widely recognized (e.g., `Http` instead of `HTTP`).\n\n> 💡 Insight: **Clarity over brevity**—a well-named variable saves hours of debugging later.\n\n**Error Handling**\nGoogle’s guide emphasizes explicit error handling. Use `Result<T, E>` for operations with failure modes, and document the possible error types in doc comments. For example:\n\n/// Returns the parsed JSON as `User`, or an `Error` if parsing fails.\nfn parse_user(json: &str) -> Result<User, Error> { ... }\n\nAvoid silent failures or ambiguous `Option` returns unless the context is clearly understood.\n\n**Documentation Standards**\nDocumentation is non-negotiable. Every public item (functions, structs, modules) must include a doc comment (`///`). Include:\n- A brief description of purpose.\n- Parameters, return values, and their meanings.\n- Examples where behavior isn’t immediately obvious.\n\n> 💡 Insight: **Document *why*, not just *what***—explain edge cases and assumptions.\n\n**Performance and Safety**\nLeverage Rust’s ownership model to avoid common pitfalls. Prefer immutable data by default (`let x = 5;` over `let mut x = 5;`). Use `Cow<Str>` for efficient string handling when ownership isn’t critical. Always prefer `&str` over `String` in function signatures unless you need ownership.\n\n**Testing and Testing**\nWrite unit tests for critical logic using `#[test]` attributes. Integration tests should live in a `tests/` directory. Mock external dependencies (e.g., databases) using crates like `mockall`. Ensure tests cover error cases and edge conditions.\n\n## 🎯 Real-World Impact\n- **Reduced Bugs**: Consistent error handling and documentation cut down on runtime panics and miscommunication.\n- **Faster Onboarding**: Clear conventions help new developers understand the codebase quickly.\n- **Maintainability**: Structured naming and documentation make refactoring safer and less error-prone.\n\n## ✨ Conclusion\nGoogle’s Rust Style Guide is more than a checklist—it’s a philosophy for writing robust, team-friendly Rust code.
